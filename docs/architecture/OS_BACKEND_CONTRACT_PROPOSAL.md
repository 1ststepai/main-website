## Decision and ownership

Use an **organization → portfolio → project** OS domain behind the existing public onboarding, with deterministic projections first and independently authorized evidence acquisition second. The browser remains a disposable preview until a user explicitly saves. An authenticated service owns durable Projects, decisions, evidence, and generated artifacts; provider sessions, GitHub installations, portfolio cards, and UI stages never become the project source of truth. Separate permissioned workers handle repository inspection, research, audit, compilation, and agent jobs. Every derived output records its input revisions so new evidence invalidates stale recommendations rather than silently upgrading them.

The public-site agent owns `/os` experience and this proposal. Backend ownership, hosting boundary, and any shared identity or `app.1ststep.ai` integration require Evan's decision and a contract to the dedicated app Engineering Orchestrator; this document grants no authority to edit app-owned auth, persistence, APIs, database, or release systems. A separate OS service is the recommended boundary because OS projects and Job Agent applications have different data and permissions. Reusing an identity provider may be evaluated only after a tenant/consent contract; shared identity must not mean shared records or implicit cross-product access.

Alternatives: putting all OS state in the browser loses durability and authorization; embedding OS directly in the Job Agent service couples unrelated tenants and release gates; making an LLM conversation the source of truth loses deterministic revision, evidence, and resume semantics. A separate OS service adds an operational component, justified only when Save/Create is approved for P0. Until then the current local preview is the correct implementation.

## Invariants and canonical data

- Every persisted entity has `schemaVersion`, immutable `id`, `organizationId` where tenant-owned, creation/update timestamps, and revision/ETag where mutable. IDs are opaque; the server derives organization and actor from authentication, never a client-selected tenant field. A project belongs to exactly one portfolio and organization; a user may have memberships in many projects. All reads/writes require organization membership **and** project-specific authorization. Portfolio visibility is the union of explicitly authorized projects, not blanket access to an organization's projects. Audit logs retain actor, reason, before/after revision pointers, and request ID.
- Unknown is an explicit status or `null`, never `false`, zero, an empty list, or a passing check. Boolean `false` means observed or user-confirmed negative. Every **inferred** field is a `Fact` with `value`, `source`, `confidence`, `status`, and `observedAt`; the schema also permits evidence references. Confidence is calibrated by method, not a fabricated percentage.
- Inputs and evidence are immutable/versioned. Project and profile are mutable aggregates with optimistic concurrency. A decision points to the exact recommendation/profile revision it accepted; changing an input marks dependent decisions/recommendations `STALE` until recomputed or re-confirmed. Immutable baseline and finding IDs survive remediation. Deletion/retention requires separate owner policy.
- Secrets, repository content, and sensitive answers stay server-side in bounded stores partitioned by organization **and project**. Analytics receives enumerated mode/stage/action only. Rendered artifacts are untrusted until validation; no generated file grants an agent authority merely by its filename. Project A context never enters Project B merely because both share an owner; only reviewed, sanitized, explicitly permitted pattern knowledge can cross the boundary.

The JSON Schema defines versioned `User`, `Organization`, `OrganizationMembership`, `Portfolio`, `ProjectMembership`, `Project`, `ProjectRegistryRecord`, `ProjectProfile`, `ProjectGenome`, `GenomeSignal`, `CapabilitySelection`, `Answer`, `Recommendation`, `Evidence`, `Decision`, `ProjectOSManifest`, `ProjectOSArtifact`, `Connection`, `AuditRun`, `AutomationOpportunity`, `DiscoveryProfile`, `AgentJob`, `Checkpoint`, `Handoff`, `ResearchClaim`, `BaselineSnapshot`, `AuditFinding`, `ReleaseRecord`, `OutcomeObservation`, `PatternDefinition`, `PortfolioCommandCenterSnapshot`, `Fact`, and `UniversalTaskEnvelope`. The separate [agent session lifecycle contract](OS_AGENT_SESSION_LIFECYCLE_CONTRACT.md) adds proposed `Agent`, `AgentRuntime`, `AgentSession`, `AgentCheckpoint`, and `SessionRotation` entities without equating a durable Agent to a provider conversation or altering the existing job/checkpoint meanings. `ProjectGenome` is a revisioned snapshot; `GenomeSignal` records each claim with status, source, confidence, and provenance. `ProjectProfile` carries narrative and starting-state details, while Genome is the interpreted, evidence-aware machine view. Schema major versions are additive only within v1; breaking changes require v2 plus explicit migration and dual-read compatibility period. Schema validation is necessary but not sufficient for tenant authorization or business-state transitions.

## Portfolio, project registry, and first-party dogfooding

`Organization` owns many `Portfolio` records; each `Portfolio` contains many `Project` records. A Project has one immutable organization identity and one current portfolio assignment, with independent Genome, OS manifests, connections, evidence, audits/findings, decisions, releases, Discovery state, and jobs. A `ProjectMembership` gives a user a project role; organization membership alone does not grant repository or artifact access. A project move between portfolios changes the assignment through an audited ownership operation requiring rights on both portfolios; moving across organizations is a separate migration with no implicit data transfer. Project names and slugs are display and routing values, never authorization keys.

`ProjectRegistryRecord` is the **canonical read projection** for a portfolio row, rebuilt from authorized project records and pinned source revisions, not a second writeable project ledger. It contains project/organization/portfolio IDs, name/slug, canonical URL and repository reference, product type, stage, platforms, stack, auth, database, payments, AI providers, deployment, analytics, business and growth models, public/release/audit states, current Genome and OS manifest versions, health by dimension, open critical/high finding counts, last verified timestamp, and current next action. Optional or unobserved values are explicit `Fact(status=UNKNOWN,value=null)`. The UI displays unknown health as “Not assessed” until applicable controls and evidence support it; a missing release is not a failed release. Registry reads require per-project authorization and return only safe summaries, not raw repository snippets or secrets.

The **first-party dogfooding target list supplied by Evan** is 1stStep OS, `app.1ststep.ai` / AI Job Agent, DaySetGo, SwingTradePros, Real-Rank.ai, and Unveiling Rarities. This list supplies future registry seeds and varied regression targets, **not verified imported OS records** or proof of current public status, stack, maturity, deployment, audit, or ownership metadata. Each import needs a verified organizational owner, consent/permission, project role, source connection, and baseline; the `app.1ststep.ai` orchestrator retains app implementation authority. After verification, these projects can supply audit-control evidence, engineering patterns, business/growth lessons, and regression cases. Internal project data stays private unless Evan explicitly approves a specific public artifact. Different project types should test whether controls, modules, and patterns remain applicable without forcing a SaaS template.

Create New, Import Existing, and Add Another all create a distinct Project under an authenticated user's chosen authorized Organization/Portfolio. Import provenance records provider, source identity, consent, import job, and baseline status. P0 may support new project and one read-only GitHub import. GitLab, Bitbucket, archives, approved local workflows, and manual descriptions are later connector types with separate permissions/threat reviews; a manual description creates only user-provided facts. Import never merges projects by name, URL, or repository string, and retries use an idempotency key. A shared repository can be connected to more than one Project only through explicit separate grants and isolated evidence copies/references.

The future `PortfolioCommandCenterSnapshot` is a read-only, authorization-filtered projection with per-project product, engineering, security, testing, design, AI efficiency, business, discovery, growth, operations, and release-readiness health; current audit/release state; open P0/P1 findings; active jobs; measured AI/infrastructure spend; growth state; and top next action. Every metric includes source, as-of time, coverage, and `UNKNOWN` when unavailable; the UI may render that state as “Not assessed.” Aggregates disclose neither unauthorized project existence nor private details. No command-center UI is in this cycle.

## Genome and adaptive questions

Genome inputs are **same-project** user answers, repository observations, externally sourced research, business-system evidence, public-product evidence, previous decisions, existing OS artifacts, and explicitly approved PatternDefinitions. Raw observations, decisions, or OS files from another project are never direct Genome inputs. Each signal has one of `UNKNOWN`, `INFERRED`, `RECOMMENDED`, `CONFIRMED`, `OBSERVED`, `VERIFIED`, `CONTRADICTED`, `STALE`. `CONFIRMED` means the user affirmed it, `OBSERVED` means a permitted source was inspected, and `VERIFIED` means an explicit verification method passed. Contradictory observations remain as separate evidence; the resolver emits `CONTRADICTED` until reviewed. Time-sensitive observations can become `STALE` by source-specific TTL without erasing history. A source's absence is `UNKNOWN`, never proof of a negative.

Reducer inputs are version-pinned and domain-neutral: project type is not assumed to be SaaS. A policy registry maps signal conditions to relevant capability, audit control, research task, agent role, gate, provider requirement, and OS module. Registry entries carry version, rationale, and activation predicates; unsupported cases remain inactive. The reducer is deterministic for identical input revisions, registry version, and clock boundary. Recompute creates a new snapshot, not an edit of the old one.

A question is eligible only if its possible answers can materially change a named Genome signal, capability, risk, architecture, recommendation, research/audit scope, business model, or growth plan. Store `questionId`, `policyVersion`, `affectedOutputs`, `estimatedInformationGain`, `reason`, `options`, and `answerStatus`. Rank by impact and uncertainty, cap each session to a small number, and stop when remaining eligible questions do not change an immediate decision. `RECOMMEND_FOR_ME` produces a sourced recommendation to confirm; `I_DONT_KNOW` records unknown and may trigger safe research or defer the dependent decision. Neither is coerced into `false`. Experienced users may supply evidence or skip beginner explanations; all modes use the same state semantics.

## Evidence, research, and recommendations

`Evidence` captures source class (`USER_PROVIDED`, `REPOSITORY_OBSERVED`, `EXTERNAL_RESEARCH`, `BUSINESS_SYSTEM_OBSERVED`, `PUBLIC_PRODUCT_OBSERVED`, `INFERENCE`, `ASSUMPTION`), locator, content digest, retrieval/observation time, scope, access grant, redaction state, and confidence. `ResearchClaim` additionally has claim text, source URL/reference, retrieved date, freshness/expiry rule, contradictions, and verification state. External claims are not `VERIFIED` just because a URL exists. An inference cites its inputs and transformation; an assumption says what would falsify it.

Each recommendation cites input revisions and relevant claims, distinguishes its evidence class, names the decision it affects, offers an uncertainty statement, and has an expiry/invalidation rule. A cross-project pattern can recommend a **hypothesis** only when its scope matches this Project and its sanitized evidence is authorized; it cannot certify this project's health. No research claim is emitted by the deterministic preview. User-provided answers may justify preliminary guidance but not external-research language. Fetching external pages requires source allowlists/SSRF controls, provenance, terms/privacy review, and a declared budget.

The current email request can be described as a **free first-look request**, not a completed audit or guaranteed response. Prefer useful, candid findings over mocking the customer.

Evaluate a GitHub App with selected-repository installation and server-side installation tokens. Proposed initial repository permissions: **Metadata: read** and **Contents: read**. Do not ask for Issues, Pull requests, Actions, Checks, Workflows, Administration, or organization permissions by default. Flow: authenticated OS member chooses Connect → server creates signed, expiring intent bound to actor/project/nonce → GitHub installation screen selects repositories → server validates callback and installation ownership → user explicitly selects target repo and branch → server checks repo ID remains in installation allowlist → mints a repository-restricted short-lived installation token in a worker → records immutable owner/repo ID, branch/ref, commit SHA, permission snapshot and fetch manifest → inspects bounded files → records baseline evidence and audit job. Tokens never reach browser, logs, artifacts, or AI prompts. Store app private key in approved secret manager; encrypt installation metadata; verify webhook signatures if webhooks are later used. Disconnect revokes local access and prevents new jobs; GitHub installation revocation is observed/handled separately. A pasted URL is only a locator, never proof of access. No broad PAT prompt.

`BaselineSnapshot` is finalized atomically after collecting what was actually accessible: repo ID, branch, immutable commit SHA/tree digest, dirty/applicable state (`UNKNOWN` for remote working tree), timestamp, stack/dependencies, test/build state with execution method, known deployment/external-system evidence, and Genome revision. If no tests ran, `testState=NOT_RUN`, never `PASS`. Every observation references content digest and the baseline commit. A partial failure yields an incomplete draft and cannot be sealed as a full baseline. Once sealed, snapshot and digest are append-only. Remediation creates a new checkpoint/delta against the original; it never rewrites the baseline. Repo access is checked again at job start and results are scoped to the selected project; no cross-tenant cache exposure.

## Audit integration and verification

The control registry covers applicable domains across product, architecture, engineering, security/privacy/auth/database, testing/accessibility/UX/performance, AI efficiency, deployment/observability/continuity, business/pricing/competitors, SEO/AI discovery/growth/sales/customer success, automation/analytics/billing/migration/operations, and release readiness. A control declares applicability predicates, required evidence strength, method, and version. Non-applicable controls are `NOT_APPLICABLE` with reason; inaccessible controls are `NOT_ASSESSED`, not clean. No global score in P0 unless denominator, weights, missing data, and uncertainty are reviewed. Scope a first audit to the user's highest-risk path and available evidence.

An `AuditFinding` has immutable ID, domain/control version, severity, **separately assigned action priority** (`P0`/`P1`/`P2`/`P3`/`UNPRIORITIZED`), status, evidence references and strength, impact statement, recommendation, and verification requirement. Severity is not silently converted to priority. Lifecycle is `OPEN` → `REMEDIATED` → `VERIFIED`, with `REOPENED` and `NOT_ASSESSED` available; a code change alone only permits `REMEDIATED`. Verification must use fresh evidence and identify verifier/automated check. AuditRun pins **one project**, baseline, Genome, control set, target commit, time, and result; later runs are new records, not overwrites. Portfolio-level recurring-finding statistics may use only authorized, sanitized finding categories, never raw cross-project evidence. Read-only audit never starts remediation.

## Long-running jobs, business, and Discovery

An `AgentJob` persists **one project and organization**, task/provider/model, completed and remaining units, budget used/ceiling, current checkpoint, next action, pause reason, and trustworthy `resumeNotBefore` if known. States: `RUNNING`, `CHECKPOINTING`, `PAUSED_USAGE_LIMIT`, `PAUSED_RATE_LIMIT`, `PAUSED_CONTEXT_LIMIT`, `PAUSED_USER`, `PAUSED_ERROR`, `RESUME_READY`, `BLOCKED`, `COMPLETED`. All transitions are server-authorized, idempotent, and logged. A checkpoint stores same-project input revisions, completed artifact digests, remaining work, budget, and lease owner; resume revalidates project membership, source freshness, permissions, budget, and idempotency before continuing. A provider session ID is only an optional adapter hint. Portfolio job counts are filtered projections; no worker acquires portfolio-wide context by default. No idle polling or automatic external action is implied.

Agent identity and runtime-session identity are separate. The approved product direction is automatic lifecycle management with durable checkpoints and a two-phase handoff, subject to the [proposed lifecycle contract](OS_AGENT_SESSION_LIFECYCLE_CONTRACT.md) and closed G1 backend gate. Unsupported programmatic runtime creation is `ROTATION_REQUIRES_RUNTIME_SUPPORT`, never a simulated rotation or a request that Evan open a chat. Provider transcripts are secondary evidence, not canonical state. The read-only `/admin/agents` projection cannot perform lifecycle transitions.

## Pattern intelligence and learning loop

The learning loop is **Project → Audit → Finding → Remediation → Verification → OutcomeObservation → Pattern candidate → reviewed PatternDefinition → applicable future recommendation**. Incidents, migrations, security fixes, growth experiments, operational lessons, and cost optimizations may also produce candidates. `OutcomeObservation` pins one project's before/after facts, measurement period, evidence, and verification state; an unknown or unmeasured result stays unknown. A successful code change alone is not an outcome. The extractor can nominate a candidate, but a human or separately authorized reviewer must check evidence quality, privacy, applicability, anti-patterns, and risks before publication to a registry.

`PatternDefinition` carries ID/version, title, domain, problem, recommended pattern, source project IDs behind an access-controlled internal reference, sanitized supporting evidence and outcome references, applicability predicates, anti-patterns, risks, confidence, last verified time, review status, and `INTERNAL` audience in the draft schema. Broader use requires a separately approved sanitized publication contract, not direct serialization of internal provenance. One project's practice remains a low-confidence candidate, not a universal rule. Cross-customer comparisons require separate opt-in and a privacy review; aggregate results must meet minimum cohort/suppression thresholds before use, with no customer names, source code, secrets, or identifiable rare attributes. Pattern recommendations cite pattern version, applicability rationale, and this project's own evidence gap. Revocation or new contradictory evidence marks affected recommendations stale.

## Threat model and non-negotiable controls

| Threat | Proposed control / verification |
| --- | --- |
| Repository prompt injection and malicious files | Treat all repo text as data. Structured extractor, file/type/size allowlists, quarantine, no execution by default, instruction/data separation, output validation, adversarial fixture. |
| Secrets, PII, provider leakage | Preflight secret/redaction scan, minimum snippets, no raw repo sent to model without purpose/consent, encrypted storage, scoped retention/deletion, access audit. Provider/model data policy needs approval. |
| Cross-project/org access | Server-derived tenant, membership and role checks on every object/job/download, tenant-scoped queries and cache keys, negative authorization tests. |
| Same-organization project leakage | Project-scoped authorization, storage/cache/vector namespaces, model context assembly, job queues and artifact URLs; a portfolio role alone cannot read Project B repository content. Test Project A/B isolation, including shared owner and shared repo cases. |
| Pattern extraction or comparison leaking customer facts | Quarantine candidate patterns, sanitize and review evidence, audience/consent labels, cohort suppression, no raw customer data in cross-project prompts or outputs. Test revocation and rare-attribute inference. |
| Connection takeover and callback forgery | Signed expiring intent, nonce/state, installation/repo ID validation, server-held credentials, callback replay protection, webhook HMAC if used. |
| Uploaded archives and generated ZIPs | P0 excludes uploads. Later: decompression bombs, path traversal, symlink, malware, size/type limits; ZIP output path allowlist and checksums. |
| External actions and spend | Separate read/write scopes, human approval for writes/outreach, budget ceiling, idempotency, kill switch, cancellation and audit trail. |
| Stale evidence and fabricated success | Revision pinning, freshness/contradiction states, evidence-linked outputs, explicit `NOT_ASSESSED`, fresh verification before `VERIFIED`. |

The security review must include privacy notice, retention/deletion, data residency, breach/incident handling, repository-content license/terms, and provider subprocessors before live connections. This table is a threat-model proposal, not a passed penetration test.

## Cost and model routing

Default order: deterministic reducer/cache → local/reused evidence → low-cost model → balanced model → premium reasoning only when quality gates fail or task risk justifies it. Every AI task policy records task class, context estimate, model tier, input/output token budget, retry budget, fallback, cache key, expected and maximum cost, quality validator, and cutoff. Cost formula per job: `input_tokens × input_price + output_tokens × output_price + retrieval/compute/storage + retries`; use current approved vendor rates at implementation time, not a hard-coded price here. Stop before ceiling; do not silently switch to a pricier model. Expected P0 spend is **unknown** until provider choice, sample corpus, token measurements, and volume exist. A cost-free deterministic starter OS is plausible; repository/audit storage and GitHub API usage still need measurement. No paid model is enabled by this proposal.
