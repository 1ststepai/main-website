# 1stStep OS: owned backend contract and execution architecture

**Status:** proposed for Evan and the eventual OS backend owner; no backend, GitHub App, account, billing, or production change is authorized by this document. **Source baseline:** local `/os/start/` commit `cefa5c8c1be9f0039aec83c0e87a6795400b1d5e`. **Contract version:** `os.contract/1.0-draft`. The [versioned entity schema](os-contract.v1.schema.json) is a wire/storage-shape proposal, not a migration or claim of a live service.

## Decision and ownership

Use a **project-centered OS domain** behind the existing public onboarding, with deterministic projections first and independently authorized evidence acquisition second. The browser remains a disposable preview until a user explicitly saves. An authenticated service owns durable Projects, decisions, evidence, and generated artifacts; provider sessions, GitHub installations, and UI stages never become the project source of truth. Separate permissioned workers handle repository inspection, research, audit, compilation, and agent jobs. Every derived output records its input revisions so new evidence invalidates stale recommendations rather than silently upgrading them.

The public-site agent owns `/os` experience and this proposal. Backend ownership, hosting boundary, and any shared identity or `app.1ststep.ai` integration require Evan's decision and a contract to the dedicated app Engineering Orchestrator; this document grants no authority to edit app-owned auth, persistence, APIs, database, or release systems. A separate OS service is the recommended boundary because OS projects and Job Agent applications have different data and permissions. Reusing an identity provider may be evaluated only after a tenant/consent contract; shared identity must not mean shared records or implicit cross-product access.

Alternatives: putting all OS state in the browser loses durability and authorization; embedding OS directly in the Job Agent service couples unrelated tenants and release gates; making an LLM conversation the source of truth loses deterministic revision, evidence, and resume semantics. A separate OS service adds an operational component, justified only when Save/Create is approved for P0. Until then the current local preview is the correct implementation.

## Invariants and canonical data

- Every persisted entity has `schemaVersion`, immutable `id`, `organizationId` where tenant-owned, creation/update timestamps, and revision/ETag where mutable. IDs are opaque; the server derives organization and actor from authentication, never a client-selected tenant field. All reads/writes are scoped to membership plus project role. Audit logs retain actor, reason, before/after revision pointers, and request ID.
- Unknown is an explicit status or `null`, never `false`, zero, an empty list, or a passing check. Boolean `false` means observed or user-confirmed negative. Every **inferred** field is a `Fact` with `value`, `source`, `confidence`, `status`, and `observedAt`; the schema also permits evidence references. Confidence is calibrated by method, not a fabricated percentage.
- Inputs and evidence are immutable/versioned. Project and profile are mutable aggregates with optimistic concurrency. A decision points to the exact recommendation/profile revision it accepted; changing an input marks dependent decisions/recommendations `STALE` until recomputed or re-confirmed. Immutable baseline and finding IDs survive remediation. Deletion/retention requires separate owner policy.
- Secrets, repository content, and sensitive answers stay server-side in bounded stores. Analytics receives enumerated mode/stage/action only. Rendered artifacts are untrusted until validation; no generated file grants an agent authority merely by its filename.

The JSON Schema defines these versioned entities: `User`, `Organization`, `OrganizationMembership`, `Project`, `ProjectProfile`, `ProjectGenome`, `GenomeSignal`, `CapabilitySelection`, `Answer`, `Recommendation`, `Evidence`, `Decision`, `ProjectOSManifest`, `ProjectOSArtifact`, `Connection`, `AuditRun`, `AutomationOpportunity`, `DiscoveryProfile`, `AgentJob`, `Checkpoint`, `Handoff`, plus `ResearchClaim`, `BaselineSnapshot`, `AuditFinding`, `Fact`, and `UniversalTaskEnvelope`. `ProjectGenome` is a revisioned snapshot; `GenomeSignal` records each claim with status, source, confidence, and provenance. `ProjectProfile` carries narrative and starting-state details, while Genome is the interpreted, evidence-aware machine view. Schema major versions are additive only within v1; breaking changes require v2 plus explicit migration and dual-read compatibility period. Schema validation is necessary but not sufficient for tenant authorization or business-state transitions.

## Lifecycle and service boundaries

| Boundary | Owns | Input → output | Hard boundary |
| --- | --- | --- | --- |
| Public `/os/start/` | UI, ephemeral answers and preview projection | Five modes → preview and optional Save/Create request | Never stores tokens or claims verified evidence. |
| Identity/project service | Membership, project claim, profile, answers, decisions | Authenticated intent → durable Project and revision | Must enforce tenant/project authorization and idempotency. Backend owner TBD. |
| Genome/question service | Deterministic signal reducers, question eligibility, capability selection | Versioned inputs → Genome snapshot, next eligible question | Does not turn inferred into observed. |
| Evidence/research service | Provenance, retrieval, contradiction and freshness | Explicit source grant/job → immutable Evidence/ResearchClaim | No unreported browsing, private-source access, or citation laundering. |
| Connector/inspector | GitHub installation binding, bounded read-only fetch, fingerprint | Authorized repo/ref → sealed baseline/evidence | Never accepts a URL as authorization or runs repository instructions. |
| Audit service | Applicable controls, runs, findings, verification | Baseline + Genome + control version → AuditRun | No score or finding without evidence and control applicability. |
| Compiler/export | Module selection, validated artifacts, ZIP export | Frozen revisions → manifest/artifacts/download | No external write; future PR is separate permission/action. |
| Job/handoff service | Universal task envelopes, budgets, checkpoints, provider adapters | Approved task → auditable Job/Checkpoint/Handoff | Provider state is a cache, not canonical workflow state. |

These are logical boundaries, not a demand for eight deployables. P0 can be one service plus a bounded background worker and a relational store/object store. The service's transactional database is canonical for metadata/revisions; encrypted object storage holds immutable large evidence/artifacts keyed by digest. A job queue is introduced only for work exceeding request limits. No vendor or database is selected by this proposal.

**App-orchestrator handoff contract, if shared identity or app navigation is chosen:** public `/os` owner specifies the entry/return URL, authenticated subject and tenant mapping, consent scopes, session boundary, allowed data fields, error/expiry behavior, attribution restrictions, and visible truth states; app orchestrator decides and implements any app-owned auth/API/database changes in its own worktree. Joint acceptance must include wrong-account, revoked membership, expired session, cross-org project access, and independent release/rollback checks. No OS repository contents, draft answers, or GitHub credentials cross into Job Agent by default. A handoff is `PROPOSED` until the app orchestrator accepts its scope and ownership; public-side design cannot silently turn it into app work.

## API proposal and UI mapping

All endpoints below are **proposed** under `/api/os/v1`; none exists today. Authenticate protected calls, enforce membership on each resource, use `Idempotency-Key` for creation/jobs and `If-Match` revision for edits, return stable error codes (`VALIDATION`, `UNAUTHORIZED`, `FORBIDDEN`, `CONFLICT`, `STALE_REVISION`, `SOURCE_UNAVAILABLE`, `BUDGET_EXCEEDED`). `202` means accepted job, not completed outcome. Async operations expose status, safe retry, cancellation, and evidence references. Avoid putting goal text or secrets in URLs/logs.

| Current local object/stage | Future entity and call | UI truth rule |
| --- | --- | --- |
| `mode`, `originUnsure`, `goal`, `goalConfirmed` / choose, describe, route, interpret | `Project.startingState`, `ProjectProfile.goal`, `Answer`; `POST /projects` only after Save/Create | Keep interpretation local until claim succeeds; do not call it saved on request start. |
| `answers`, `qIndex`, `questions[mode]` | `Answer[]` and versioned question-selection policy; `PUT /projects/{id}/answers/{key}`, `GET /projects/{id}/next-question` | Server returns question ID, reason, Genome revision, and option semantics; client renders existing stages. |
| `deriveGenome`, `deriveCapabilities` | `ProjectGenome`, `GenomeSignal`, `CapabilitySelection`; `GET /projects/{id}/state` | Display source/status and revision; stale or unresolved fields stay unknown. |
| `acceptedRecommendations`, `openRecommendations`, `recommendationChanges` | `Recommendation`, `Decision`; `POST /projects/{id}/decisions` | A changed recommendation is a proposed decision, not automatically accepted. |
| connect, baseline | `Connection`, `BaselineSnapshot`; `POST /connections/github/intent`, `POST /projects/{id}/baseline-jobs` | Connector permissions shown before redirect; no scan claim until finalized snapshot exists. |
| recommend, reveal, next | `Recommendation[]`, `ProjectOSManifest`, `ProjectOSArtifact`; `POST /projects/{id}/compile-jobs`, `GET /projects/{id}/exports/{manifestId}` | Preview remains labeled until completed manifest and downloadable archive exist. |
| existing audit / business / growth projections | `AuditRun`, `AutomationOpportunity`, `DiscoveryProfile`; read endpoints | No personalized finding, ROI, ranking, or measured discovery score without evidence. |

`POST /projects` accepts a schema-valid minimum profile after the user authenticates and, **only if anonymous draft storage is separately approved**, a short-lived server-issued draft claim token; server derives owner/organization. It returns project ID, revision, and accepted answer IDs only after commit. `GET /projects/{id}/state` returns one consistent projection `{project, profile, genome, capabilities, recommendations, pendingJobs, revision}` to avoid UI races. Uploads and provider callbacks are separate endpoints with independent security review. UI can progressively swap its pure local derivation for this projection, retaining its current stage components and offline preview. A full front-end rewrite is not a prerequisite.

## Genome and adaptive questions

Genome inputs are user answers, repository observations, externally sourced research, business-system evidence, public-product evidence, previous decisions, and existing OS artifacts. Each signal has one of `UNKNOWN`, `INFERRED`, `RECOMMENDED`, `CONFIRMED`, `OBSERVED`, `VERIFIED`, `CONTRADICTED`, `STALE`. `CONFIRMED` means the user affirmed it, `OBSERVED` means a permitted source was inspected, and `VERIFIED` means an explicit verification method passed. Contradictory observations remain as separate evidence; the resolver emits `CONTRADICTED` until reviewed. Time-sensitive observations can become `STALE` by source-specific TTL without erasing history. A source's absence is `UNKNOWN`, never proof of a negative.

Reducer inputs are version-pinned and domain-neutral: project type is not assumed to be SaaS. A policy registry maps signal conditions to relevant capability, audit control, research task, agent role, gate, provider requirement, and OS module. Registry entries carry version, rationale, and activation predicates; unsupported cases remain inactive. The reducer is deterministic for identical input revisions, registry version, and clock boundary. Recompute creates a new snapshot, not an edit of the old one.

A question is eligible only if its possible answers can materially change a named Genome signal, capability, risk, architecture, recommendation, research/audit scope, business model, or growth plan. Store `questionId`, `policyVersion`, `affectedOutputs`, `estimatedInformationGain`, `reason`, `options`, and `answerStatus`. Rank by impact and uncertainty, cap each session to a small number, and stop when remaining eligible questions do not change an immediate decision. `RECOMMEND_FOR_ME` produces a sourced recommendation to confirm; `I_DONT_KNOW` records unknown and may trigger safe research or defer the dependent decision. Neither is coerced into `false`. Experienced users may supply evidence or skip beginner explanations; all modes use the same state semantics.

## Evidence, research, and recommendations

`Evidence` captures source class (`USER_PROVIDED`, `REPOSITORY_OBSERVED`, `EXTERNAL_RESEARCH`, `BUSINESS_SYSTEM_OBSERVED`, `PUBLIC_PRODUCT_OBSERVED`, `INFERENCE`, `ASSUMPTION`), locator, content digest, retrieval/observation time, scope, access grant, redaction state, and confidence. `ResearchClaim` additionally has claim text, source URL/reference, retrieved date, freshness/expiry rule, contradictions, and verification state. External claims are not `VERIFIED` just because a URL exists. An inference cites its inputs and transformation; an assumption says what would falsify it.

Each recommendation cites input revisions and relevant claims, distinguishes its evidence class, names the decision it affects, offers an uncertainty statement, and has an expiry/invalidation rule. No research claim is emitted by the deterministic preview. User-provided answers may justify preliminary guidance but not external-research language. Fetching external pages requires source allowlists/SSRF controls, provenance, terms/privacy review, and a declared budget.

## GitHub read-only connection and immutable baseline

Evaluate a GitHub App with selected-repository installation and server-side installation tokens. Proposed initial repository permissions: **Metadata: read** and **Contents: read**. Do not ask for Issues, Pull requests, Actions, Checks, Workflows, Administration, or organization permissions by default. GitHub documents that app permissions start empty and should be minimal; installation tokens can be restricted to specified repository IDs and expire after one hour. Reading workflow files through the Contents API must be verified endpoint by endpoint; a permission expansion, if genuinely necessary, requires a new review. [GitHub permissions](https://docs.github.com/en/apps/creating-github-apps/registering-a-github-app/choosing-permissions-for-a-github-app), [installation authentication](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/authenticating-as-a-github-app-installation), [App practices](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/best-practices-for-creating-a-github-app).

Flow: authenticated OS member chooses Connect → server creates signed, expiring intent bound to actor/project/nonce → GitHub installation screen selects repositories → server validates callback and installation ownership → user explicitly selects target repo and branch → server checks repo ID remains in installation allowlist → mints a repository-restricted short-lived installation token in a worker → records immutable owner/repo ID, branch/ref, commit SHA, permission snapshot and fetch manifest → inspects bounded files → records baseline evidence and audit job. Tokens never reach browser, logs, artifacts, or AI prompts. Store app private key in approved secret manager; encrypt installation metadata; verify webhook signatures if webhooks are later used. Disconnect revokes local access and prevents new jobs; GitHub installation revocation is observed/handled separately. A pasted URL is only a locator, never proof of access. No broad PAT prompt.

`BaselineSnapshot` is finalized atomically after collecting what was actually accessible: repo ID, branch, immutable commit SHA/tree digest, dirty/applicable state (`UNKNOWN` for remote working tree), timestamp, stack/dependencies, test/build state with execution method, known deployment/external-system evidence, and Genome revision. If no tests ran, `testState=NOT_RUN`, never `PASS`. Every observation references content digest and the baseline commit. A partial failure yields an incomplete draft and cannot be sealed as a full baseline. Once sealed, snapshot and digest are append-only. Remediation creates a new checkpoint/delta against the original; it never rewrites the baseline. Repo access is checked again at job start and results are scoped to the selected project; no cross-tenant cache exposure.

## Audit integration and verification

The control registry covers applicable domains across product, architecture, engineering, security/privacy/auth/database, testing/accessibility/UX/performance, AI efficiency, deployment/observability/continuity, business/pricing/competitors, SEO/AI discovery/growth/sales/customer success, automation/analytics/billing/migration/operations, and release readiness. A control declares applicability predicates, required evidence strength, method, and version. Non-applicable controls are `NOT_APPLICABLE` with reason; inaccessible controls are `NOT_ASSESSED`, not clean. No global score in P0 unless denominator, weights, missing data, and uncertainty are reviewed. Scope a first audit to the user's highest-risk path and available evidence.

An `AuditFinding` has immutable ID, domain/control version, severity, status, evidence references and strength, impact statement, recommendation, and verification requirement. Lifecycle is `OPEN` → `REMEDIATED` → `VERIFIED`, with `REOPENED` and `NOT_ASSESSED` available; a code change alone only permits `REMEDIATED`. Verification must use fresh evidence and identify verifier/automated check. AuditRun pins baseline, Genome, control set, target commit, time, and result; later runs are new records, not overwrites. Read-only audit never starts remediation.

## Project OS compiler, export, and universal handoff

Compiler input is a frozen tuple of Genome revision, decisions, research/evidence revisions, applicable capability set, and template/policy version. Select the **smallest sufficient** modules whose declared predicates match the project and whose dependencies are met. Starter examples: `AGENTS.md`, `PROJECT.md`, `PRODUCT_REQUIREMENTS.md`, `ARCHITECTURE.md`, `TESTING.md`; add `SECURITY.md`, `DECISIONS.md`, `RESEARCH.md`, `BUSINESS.md`, `PRICING.md`, `DISCOVERY.md`, `GROWTH.md`, `OPERATIONS.md`, `agents/`, `workflows/`, `gates/`, `state/`, `schemas/` only when justified. Recovery OS may add `BASELINE.md`, `AUDIT_PLAN.md`, and `REMEDIATION.md`. Every artifact records schema/template version, authority, provenance, generated time, input dependencies, digest, and regeneration rule. Unsafe paths, duplicate names, or references to unverified facts fail compilation. Generated files must visibly label unknowns and proposed decisions.

P0 export is a deterministic ZIP: canonical provider-neutral files plus manifest, provenance, and checksums. The export endpoint is authenticated, short-lived, and bound to project role; sanitize ZIP paths and cap size/file count. A download is not a GitHub write. Future GitHub commit/PR, Claude Code, Codex, Gemini, Cursor, Copilot, Windsurf, enterprise, custom, and local-model adapters consume the same `UniversalTaskEnvelope` with objective, scope, authority, relevant files, context budget, allowed tools, acceptance criteria, tests, risk, cost ceiling, checkpoint, next action. Adapters may narrow authority, never widen it. A provider cannot change canonical decisions or claim tests passed without evidence.

## Long-running jobs, business, and Discovery

An `AgentJob` persists project/task/provider/model, completed and remaining units, budget used/ceiling, current checkpoint, next action, pause reason, and trustworthy `resumeNotBefore` if known. States: `RUNNING`, `CHECKPOINTING`, `PAUSED_USAGE_LIMIT`, `PAUSED_RATE_LIMIT`, `PAUSED_CONTEXT_LIMIT`, `PAUSED_USER`, `PAUSED_ERROR`, `RESUME_READY`, `BLOCKED`, `COMPLETED`. All transitions are server-authorized, idempotent, and logged. A checkpoint stores input revisions, completed artifact digests, remaining work, budget, and lease owner; resume revalidates project authority, source freshness, permissions, budget, and idempotency before continuing. A provider session ID is only an optional adapter hint. No idle polling or automatic external action is implied.

Business intake creates a Business Genome subset of project signals and a draft Process Map with user-stated versus observed steps. `AutomationOpportunity` records process, current human effort, systems, candidate, risk, estimated implementation effort/cost, estimated time saved, ROI confidence, and required integrations. Numeric savings/ROI stay `UNKNOWN` until measured volume, handling time, error rate, and cost basis are linked as evidence. Quotes, payments, customer messages, and external actions have separate consent and human approval gates.

`DiscoveryProfile` tracks positioning, SEO/technical SEO/content, entity authority, AEO/GEO, LLM visibility/answerability/citations, directories/reviews/social/YouTube/app stores, conversion, and analytics as individually sourced signals. Self-reported channel presence is not measured visibility. Future monitoring requires an approved source, cadence, permissions, freshness rule, and measured baseline; no synthetic rank or share-of-voice claim.

## Anonymous preview to ownership

Current preview remains entirely in memory and disappears on reload. For future Save/Create, prefer a server-issued, short-lived anonymous draft capability bound to a nonce and browser session, with minimal encrypted data, expiration, one-time claim, and per-draft size/rate limits. Begin auth only after the user requests durable value. On return, exchange the capability once in a server transaction that binds the new Project to the authenticated user and explicitly selected organization. Regenerate session, validate CSRF/state, reject replay, and show a clear conflict if already claimed. Never claim by project ID, email address, repository URL, client-supplied organization ID, or an unverified callback. Anonymous drafts cannot connect repositories, launch paid jobs, or access other tenants. If privacy/storage policy is not approved, submit the preview only after login rather than persisting anonymous drafts.

## Threat model and non-negotiable controls

| Threat | Proposed control / verification |
| --- | --- |
| Repository prompt injection and malicious files | Treat all repo text as data. Structured extractor, file/type/size allowlists, quarantine, no execution by default, instruction/data separation, output validation, adversarial fixture. |
| Secrets, PII, provider leakage | Preflight secret/redaction scan, minimum snippets, no raw repo sent to model without purpose/consent, encrypted storage, scoped retention/deletion, access audit. Provider/model data policy needs approval. |
| Cross-project/org access | Server-derived tenant, membership and role checks on every object/job/download, tenant-scoped queries and cache keys, negative authorization tests. |
| Connection takeover and callback forgery | Signed expiring intent, nonce/state, installation/repo ID validation, server-held credentials, callback replay protection, webhook HMAC if used. |
| Uploaded archives and generated ZIPs | P0 excludes uploads. Later: decompression bombs, path traversal, symlink, malware, size/type limits; ZIP output path allowlist and checksums. |
| External actions and spend | Separate read/write scopes, human approval for writes/outreach, budget ceiling, idempotency, kill switch, cancellation and audit trail. |
| Stale evidence and fabricated success | Revision pinning, freshness/contradiction states, evidence-linked outputs, explicit `NOT_ASSESSED`, fresh verification before `VERIFIED`. |

The security review must include privacy notice, retention/deletion, data residency, breach/incident handling, repository-content license/terms, and provider subprocessors before live connections. This table is a threat-model proposal, not a passed penetration test.

## Cost and model routing

Default order: deterministic reducer/cache → local/reused evidence → low-cost model → balanced model → premium reasoning only when quality gates fail or task risk justifies it. Every AI task policy records task class, context estimate, model tier, input/output token budget, retry budget, fallback, cache key, expected and maximum cost, quality validator, and cutoff. Cost formula per job: `input_tokens × input_price + output_tokens × output_price + retrieval/compute/storage + retries`; use current approved vendor rates at implementation time, not a hard-coded price here. Stop before ceiling; do not silently switch to a pricier model. Expected P0 spend is **unknown** until provider choice, sample corpus, token measurements, and volume exist. A cost-free deterministic starter OS is plausible; repository/audit storage and GitHub API usage still need measurement. No paid model is enabled by this proposal.
