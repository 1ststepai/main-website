## Root 1stStep OS Audit verdict

**Primary recommendation: PROJECT, with an Audit capability exposed to OS through a contract.** `DECISIONS.md` ADR-001 calls it a distinct companion product; `ARCHITECTURE.md` and `INTEGRATION_CONTRACT.md` give it an independent local-first, engine-first audit/recovery mission, not a mere website widget. Retain its separate source/engine boundary and ability to be independently released; make OS the upstream capability/profile/gate vocabulary and Audit the authoritative **audit-specific** control, evidence-strength, baseline, scoring, finding-history and recovery semantics. Whether it will be sold separately is unverified and not needed to choose the engineering boundary.

Actual capability is foundation-only: 15 audit schemas, 52 seed controls across 33 domains and 11 project types, a fixture/reference scoring and recovery-plan conformance script. There is no product scanner, immutable snapshot store, ledger, CLI implementation, real scoring engine, report generator, connector, UI, real run, or deployment. `python tools/validate_foundation.py` **failed 5 upstream-lock checks** today: two new OS schemas are unpinned and three pinned schemas drifted. It still calculates a fixture score, which is **test data**, not an observed project health score. `package.json` points to a non-existent `engine/src/cli.ts`; package scripts cannot prove a working CLI.

The **designed** truth model is sounder than a free-floating “roast”: `BASELINE_POLICY.md` requires a sealed source identity and manifest; `EVIDENCE_POLICY.md` separates upstream evidence state from E0–E4 strength and live from repository planes; `FINDING_SCHEMA.md` keeps lifecycle history and requires new verification after remediation; `SCORING_MODEL.md` applies deterministic evidence caps and prohibits model-set scores; `INTEGRATION_CONTRACT.md` hash-locks upstream schemas. Those are **specified/fixture-verified**, not live guarantees. A link or public page alone cannot prove private architecture, repository identity, or release readiness.

The Audit→OS Finding export is explicitly lossy: upstream `Finding` lacks audit strength/history and maps `REMEDIATED` to `FIXED_UNVERIFIED`. The Audit record must remain authoritative for audit findings. The existing integration contract also requires OS module/capability references and prefixes `audit:Gx` versus `os:Gx`. Resolve the failed hash lock by reviewing upstream changes, not silently updating pins. Audit authority has an internal status conflict: `state/CURRENT_STATE.md` says owner ratification PENDING and ADR-008…020 are individually PROPOSED, while a sentence in `DECISIONS.md` says the owner ratified audit:G1 and moved them to ACCEPTED. Treat ratification as **unresolved** until a consistent owner record exists.

Traceability is incomplete for both root systems: concept → architecture/schema is strong; implementation is shell/fixture only; the public `/os` page is a separate representation; no root-system deployment or observed end-user OS/Audit capability is established. The public site's preliminary route/recommendations are not the root deterministic module selection, and the root Audit is not the public website's future first-look request.
