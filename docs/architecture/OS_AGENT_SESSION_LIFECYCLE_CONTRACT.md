# OS agent session lifecycle contract (proposed)

**Status:** Evan approved the product requirement. This is a provider-neutral architecture and wire-contract proposal, not an operating rotation service. The separate OS backend G1 implementation gate remains **CLOSED** until an owner, platform, identity, privacy/retention, and cross-system authority are accepted. The public-site agent owns this contract and its read-only `/admin` projection; the appointed OS backend owner must implement canonical state and orchestration. App-owned agent state and runtime integration require an accepted handoff to the `app.1ststep.ai` Engineering Orchestrator. No production/runtime creation or deployment is authorized by this document.

The versioned entity shapes are in [os-agent-session-lifecycle.v1.schema.json](os-agent-session-lifecycle.v1.schema.json). They extend the existing `AgentJob`, `Checkpoint`, and `Handoff` concepts without redefining them. An `AgentJob` is a bounded task; an `Agent` is durable role identity; an `AgentSession` is one provider conversation/execution. One Agent can perform many jobs and have many historical sessions. The canonical role binding belongs to the OS ledger, never to a provider chat title, model response, local window, or CLI process list.

| Entity | Required meaning |
| --- | --- |
| `Agent` | Stable opaque ID, authority scope, owner, role, current binding revision, optional current session, and status. Project-scoped agents carry organization and project IDs; ecosystem-level roles have an explicit ecosystem scope. A binding is never inferred from a provider session ID. |
| `AgentRuntime` | Provider-neutral adapter identity, configured capability facts, observed capability time, health and supported lifecycle methods. Support for programmatic session creation must be verified per adapter and version, not assumed from an interactive CLI. No credentials in records. |
| `AgentSession` | Ephemeral runtime session ID, Agent ID, runtime ID, bounded start/end/heartbeat/lease evidence, lifecycle state, authority revision, and checkpoint pointer. A session's existence does not grant the Agent role. |
| `AgentCheckpoint` | Immutable digest-addressed snapshot of authorized project/task IDs, input revisions, branch/commit or artifact digests, completed/remaining work, next action, decisions/open gates, permission scope, budget, and expiry. It references existing Job checkpoints where applicable; it contains no transcript, secret, private repository body, or cross-project payload. |
| `SessionRotation` | Idempotent, auditable attempt linking old/new sessions and checkpoint, trigger, adapter capability, state, ordered evidence times, failure/recovery reason, and binding revisions. Exactly one attempt owns a binding change at a time. |

## Rotation and failure protocol

1. Monitor **observed** heartbeat/lease freshness, context or usage-limit signals, adapter errors, and task risk. `UNKNOWN` is not healthy. Event-driven checks or a bounded non-AI scheduler may mark stale sessions; no idle model polling or invented heartbeat is allowed. Rotation policy considers time/usage/context pressure, failed health checks, explicit operator request, and checkpoint age. Thresholds, retry ceilings, and retention await backend-owner approval.
2. Acquire a per-Agent rotation lease with idempotency key and expected binding revision. Freeze new work on the old session, create and persist an immutable `AgentCheckpoint`, and confirm its digest, authority and project scope. The old session remains bound.
3. Ask the runtime adapter whether **programmatic** `createSession` is supported. If not verified, record `ROTATION_REQUIRES_RUNTIME_SUPPORT`, keep the old binding authoritative, and surface the blocker; never describe a manually opened chat as automatic rotation. If supported, create a new isolated session with bounded retry and record its provider ID without granting role authority.
4. Generate a compact bootstrap from **canonical OS state**: Agent/role and project scope; accepted authority and current task envelope; checkpoint ID/digest; pinned source/commit and artifact references; unresolved decisions, risks and next action; tools/cost budget; verification and acknowledgment instructions. Fetch only authorized content at bootstrap time. Do not copy full conversation history. Treat old transcripts as optional secondary evidence.
5. Bootstrap the new session with narrowed authority. Verify that it can read the checkpoint and returns a structured acknowledgment containing matching Agent ID, checkpoint digest, source revision, project scope, and accepted task/authority. A model's self-assertion alone is insufficient: the OS validates the echoed fields and access/lease proofs against its ledger. Until this succeeds, the new session is a candidate with no active role binding.
6. Atomically compare-and-swap the `Agent.currentSessionId` and binding revision after acknowledgment. Only then activate the new session and revoke the old session's work lease. Request adapter retirement/close of the old session where supported, record actual result, and mark rotation `COMPLETED` only after confirmed retirement or confirmed fencing of all old-session write authority. If provider close is unsupported, fencing must still be verified; do not claim the provider conversation was destroyed.
7. Keep append-only session/rotation history. On timeout, unsupported capability, failed bootstrap, mismatched acknowledgment, lost lease, or concurrent change, record `FAILED` or `RECOVERY_REQUIRED`, fence the candidate, preserve the old binding when still safe, and retry only with an explicit idempotent policy. If the old session is unavailable, leave Agent state blocked/unknown until an authorized recovery path verifies the checkpoint and binding. Never run two sessions with the same active authority.

The two-phase boundary is **prepare** (checkpoint, create, bootstrap, verify, acknowledge) then **commit** (binding switch, old-session retirement/fencing). Each step has persisted evidence and a monotonic state transition. A failed prepare cannot switch binding. A failed commit requires reconciliation against the canonical binding revision before retry; replay must not spawn duplicate sessions or re-run completed work.

The handoff inbox belongs to the durable `Agent`, never `AgentSession`. Rotation cannot consume or discard queued entries: the new runtime binds to the same role inbox, ingests unacknowledged items, verifies their audit references against current project state, and emits its own acknowledgement receipt. Runtime compatibility metadata must include provider, runtime/version, model, and explicit messaging, create/resume/rename/receive capabilities. Unsupported or incompatible direct session resume is a runtime health incident, not OS delivery failure. The local file-backed ecosystem mailbox is a prototype; it does not provide authenticated binding or a programmatic session-creation adapter.

Automatic rotation is an internal session-lifecycle operation. It does not authorize repository edits, deployments, releases, customer contact, paid provider usage, or any other external action beyond the existing Agent authority contract and budget. The existing no-idle-model-polling rule remains in force.

## Adapter and Command Center handoff

Each provider adapter exposes capability discovery and `createSession`, `bootstrapSession`, `verifySession`, `awaitAcknowledgement`, `fenceSession`, `retireSession`, and `inspectSession` with explicit `SUPPORTED`, `UNSUPPORTED`, or `UNKNOWN` capability and bounded timeout/error outputs. Adapters may narrow authority; they cannot set OS binding or mark a rotation complete. The OS backend owns durable writes and transition validation. A Codex or Claude UI/CLI command is not an adapter contract. If creation cannot be called from the deployed OS runtime, report `ROTATION_REQUIRES_RUNTIME_SUPPORT` even if a human can open a chat in an interactive client.

The adapter also reports whether deterministic `renameSession`, `sendMessage`, and measured `getContextHealth` are supported. Names such as `app-loop-cycle-021` are usability labels only; stable Agent IDs remain unchanged. If creation or rename is unsupported, the OS records the unsupported capability and may present Evan a precise, compact manual handoff instruction with Agent, reason, old session, suggested next name and checkpoint reference. That is an **operator fallback**, not automatic rotation; the old binding remains authoritative until the new session independently verifies and acknowledges the checkpoint. The visible source directive stops midway through its manual-fallback example, so no further template is inferred.

Session policy states are `HEALTHY`, `WATCH`, `ROTATE_SOON`, `ROTATE_NOW`, `ROTATION_PREPARED`, `ROTATING`, `RETIRED`, `ROTATION_FAILED`, and `RUNTIME_SUPPORT_REQUIRED`. A state records the observed signals and policy version. Candidate signals include measured context utilization **only when exposed by the runtime**, session age, completed cycles, handoffs, superseded decisions, scope/branch changes, self-reported context pressure, checkpoint size, and conflicts with canonical state. Never fabricate exact token usage. Thresholds remain configurable and require evidence before activation. Every agent constitution should instruct the agent to emit `SESSION_ROTATION_RECOMMENDED` when continuing the current context materially increases stale-state or reasoning risk; an agent report is `AGENT_REPORTED` until verified. The public-site agent can adopt this rule in its own constitution; app-family and independent-auditor constitution changes require their authority owners.

Auditor checkpoints additionally reference baseline, open/closed/failed/pending findings, evidence, release gates, accepted risks, authority conflicts, last verdict and next audit trigger. Engineering/loop checkpoints additionally reference cycle, task, repo/branch/worktree/HEAD, finding assignments and re-audit readiness, blocked decisions, release gates, last verdict and pending handoffs. These references preserve durable evidence; they do not paste evidence bodies or full conversations into bootstrap text. Auditor rotation after a major cycle or baseline change must preserve independence rather than inherit implementer conclusions as verified facts.

The public `/admin/agents` Command Center receives **content-free** projections from each authority publisher: stable Agent ID, health, runtime label and opaque session ID, checkpoint ID/time, rotation ID/state/time, and a bounded session history. Missing or stale evidence displays `UNKNOWN`. Neither the admin UI nor its telemetry endpoint may create sessions, acknowledge a handoff, switch roles, retire sessions, or expose checkpoint/bootstrap contents. App-family projections are published by the app orchestrator; public/ecosystem projections by the appointed OS/ecosystem authority. The existing read-only Command Center is not a lifecycle backend.

## Acceptance before a live claim

- Verify backend owner, tenant/project authorization, provider credentials and retention policy under G1; define adapter support against actual APIs in the chosen runtime environment.
- Test supported, unsupported, timeout, duplicate event, stale checkpoint, mismatched scope/digest, concurrent rotation, provider close failure, and old-session death paths with durable storage and restart recovery.
- Prove exactly one active binding per Agent under concurrency; prevent work from old and candidate sessions after switch/failure respectively; revalidate job scope, permissions, source freshness, and budgets on resume.
- Confirm the Command Center shows actual, fresh publisher evidence and `ROTATION_REQUIRES_RUNTIME_SUPPORT` when creation is unavailable. Do not infer success from UI rendering, a test fixture, or a provider model's acknowledgment text alone.

**Open decisions:** named OS backend owner and platform; identity/tenant boundary and app-family contract; session and checkpoint retention; encrypted storage and provider transcript policy; adapter API capabilities; lease/heartbeat/rotation thresholds; retry and operator recovery authority. These are not guessed by this proposal.
