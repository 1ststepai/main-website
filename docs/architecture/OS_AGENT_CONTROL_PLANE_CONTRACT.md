## Authority and registry

The canonical hierarchy remains Organization → Portfolio → Projects, with explicit per-project access. First-party projects to classify, **not silently register as live**, are `1ststep.ai`, `app.1ststep.ai`, `resume.1ststep.ai`, `partners.1ststep.ai`, `1stStep OS`, and `1stStep OS Audit`. The conceptual authority topology is ecosystem lead/loop and independent ecosystem auditor; public-site/OS/Audit agents; and the app orchestrator, app loop, independent app auditor, and specialist app/resume/partners implementation agents. Names are role candidates until authority owners register stable IDs and scope. No chat title, open window, worktree, or CLI process establishes a registered Agent.

The durable `Agent` entity in [the lifecycle schema](os-agent-session-lifecycle.v1.schema.json) owns role, scope, owner, and current binding revision. A canonical Agent Registry must persist registration, allowed projects, authority contract, lifecycle status, and current session binding with optimistic concurrency and an append-only change trail. App-family Agent records remain under the app orchestrator's authority; the central OS must consume an accepted, minimized cross-system projection rather than write app-owned state directly. The existing Command Center KV snapshots are **ephemeral read models**, not that registry.

Operational states require evidence: `REGISTERED` means a durable registry record, `ONLINE` a recent valid heartbeat, `WORKING` an active task plus recent work event, `AUDITING` a current independent verification cycle, `WAITING` an explicit dependency, `BLOCKED` a dependency preventing work, `IDLE` registered and available without a task, `STALE` previously active evidence beyond the configured threshold, `OFFLINE` a registered role with no active runtime, `ROTATING` a persisted rotation attempt, and `UNKNOWN` insufficient evidence. No open chat implies `WORKING`. Thresholds and event-to-status derivation are versioned policy, not invented counters. The admin source may report a status and truth state; a future backend must derive authoritative statuses from registry, lease and event evidence.

## Event and truth contract

Every meaningful transition eventually appends an immutable `ControlPlaneEvent`: `eventId`, time, organization/portfolio/project IDs when applicable, Agent/role/runtime/session IDs, event type, entity type/ID, correlation/causation IDs, content-free summary, evidence references, source, truth state, and bounded metadata. Project-specific events never inherit a broader portfolio permission. Event IDs and causation keys are idempotent; event time and ingestion time are separate. A source cannot rewrite an audit verdict or upgrade its own report to independent verification.

Truth states are `OBSERVED` (direct system receipt), `AGENT_REPORTED` (self-report), `AUDITOR_VERIFIED` (independent audit with evidence), `SYSTEM_DERIVED` (reproducible rule over trusted evidence), and `UNKNOWN` (insufficient proof). A build message from an agent remains `AGENT_REPORTED` until a build receipt is observed. The read-only Command Center accepts a bounded subset of this envelope; unbounded metadata, source code, transcripts, credentials and customer records stay out of its feed.

Initial event families: agent registration/heartbeat/status; task accept/start/complete/block; handoff create/send/deliver/acknowledge; finding open/assign/remediate/re-audit/pass/fail; worktree/branch/commit; build/test start/pass/fail; audit start/complete; owner decision; release gate; preview create/verify; and session recommendation/checkpoint/bootstrap/create/handoff/accept/retire/fail. Only add specific event types when a real producer and consumer need them; preserve unknown vendor capabilities. The public admin Activity view filters the reported projection by project, agent, role, event type, finding, severity, cycle, time and truth state. It is not a full event archive.

## Handoff and finding authority

A durable `RoleHandoff` identifies sender Agent, recipient durable role/Agent, authority scope, related task/finding, correlation ID, owner, and evidence-backed timestamps. Route to the **current binding** of the recipient Agent. With no binding, queue it; never guess a chat destination or drop it. States are `CREATED`, `QUEUED`, `SENT`, `DELIVERED`, `ACKNOWLEDGED`, `IN_PROGRESS`, `RETURNED_FOR_VERIFICATION`, `CLOSED`, plus `RECIPIENT_OFFLINE`, `NO_ROUTE`, `BLOCKED`, and `FAILED_DELIVERY`. `SENT`, `DELIVERED`, and `ACKNOWLEDGED` are distinct receipts; an inbox file proves no more than local delivery. Acknowledgment records acceptance or rejection of authority and current status. Timeouts for unacknowledged or waiting handoffs need an owner-approved policy and real clock evidence.

The durable Finding Registry retains `AUD-*`, `ECO-AUD-*`, and future IDs, baseline, owner, severity, evidence, remediation attempt and independent verdict history. Lifecycle: `OPEN` → `ASSIGNED` → `IN_PROGRESS` → `READY_FOR_RE_AUDIT` → `RE_AUDITING` → `PASS` or `FAILED_RE_AUDIT`, with `BLOCKED` and explicitly approved `ACCEPTED_RISK` branches. Only the authorized independent auditor can produce final `PASS`. Engineering evidence can mark readiness for re-audit, never self-close an independent finding. The canonical loop is auditor → finding → loop agent → engineering orchestrator → implementation/evidence → independent re-audit. App-owned findings and app releases remain under app authority.

Communication-health rules may derive `NO_ROUTE`, `RECIPIENT_OFFLINE`, `UNACKNOWLEDGED`, `OWNER_MISSING`, `WAITING_TOO_LONG`, `READY_FOR_RE_AUDIT`, `RE_AUDIT_OVERDUE`, `STALE_IMPLEMENTATION`, `STALE_AUDIT`, and `DUPLICATE_AUTHORITY` only from persisted evidence and approved thresholds. The `/admin/decisions` projection contains only decisions that genuinely need Evan. Release records distinguish local, locally verified, independently audited, integrated, preview, hosted verified, release ready, production verified, and blocked; no local result is a production claim.

## Read-only admin boundary and acceptance

The existing admin transport has one latest encrypted metadata snapshot per public/ecosystem and app-family authority source. It cannot provide canonical durability, complete history, or delivery guarantees. Phase 1 may display a reported subset with `UNKNOWN` for missing/stale sources; it may not merge, deploy, mutate repositories, run shell commands, restart agents, alter auth, close findings, or approve releases. The future OS backend must own durable registry/event/handoff/finding transactions and publish minimized snapshots through the existing source-specific ingress; the app orchestrator must accept its publisher contract first.

Before claiming a live control plane, verify registered Agent IDs against both authority owners; heartbeat and task receipts; actual build/test/audit evidence; sent/delivered/acknowledged distinction; offline queue/replay and idempotency; independently restricted finding PASS; cross-project isolation; duplicate authority detection; source freshness; and a read-only browser path on mobile and desktop. A build, static schema, or screenshot alone is not that proof.
