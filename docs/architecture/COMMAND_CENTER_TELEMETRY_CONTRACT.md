# Admin Command Center telemetry contract (Phase 1)

The Command Center lives inside the existing protected `1ststep.ai/admin` Studio. Its UI makes **GET** requests only. It has no deploy, merge, repository mutation, agent-control, audit-acknowledgement, or release-gate actions. The admin session protects reads; a separate publisher credential permits metadata-only telemetry ingestion. The ingestion endpoint is internet-reachable but rejects requests without the source-specific credential.

## Current truth

The first-party ecosystem auditor currently writes immutable audits and manager/loop inbox handoffs to its **local** `state/` directory. Its integration record explicitly says there is no verified live manager/loop subscriber. The public site runs on Vercel and cannot read those local files. No existing central agent registry, heartbeat service, or app-family telemetry publisher has been verified. Consequently, a deployed Command Center will show `UNKNOWN`/unconnected until the authority owners publish evidence under this contract. A worktree is not evidence that an agent is running, and an inbox file is not acknowledgement.

The isolated ecosystem auditor infrastructure branch additionally persists content-free role mailbox pointers and per-session consumption receipts. The auditor collector can project those records as separate `osDelivery` (`AVAILABLE_TO_RECIPIENT`), `runtimeConsumption` (`UNREAD`, `INGESTED`, `ACKNOWLEDGED`, `IN_PROGRESS`) and `runtimeDelivery` (`WAITING_FOR_RUNTIME`, `RUNTIME_INCOMPATIBLE`, `ACKNOWLEDGED`) fields. Its old handoff files alone project OS delivery `UNKNOWN` and never imply an acknowledgement. A runtime/model incompatibility leaves the persisted handoff retained and points to an adapter or upgrade action. Cycle 2 is displayed only if its real audit and mailbox records are present; a synthetic test fixture is not live incident telemetry. No automatic publisher or subscription has been deployed, so local receipt changes do not appear in hosted `/admin` in real time until an authorized publisher is connected and refreshed. The OS owner sets that cadence and stale threshold; this admin remains a read-only projection.

## Source ownership and transport

Two independent producer identities are accepted:

- `public-ecosystem`: Ecosystem Lead / Loop Agent, ecosystem auditor, public-site engineer, OS and Audit agents. The public/ecosystem owner integrates this publisher with canonical local handoff and agent state.
- `app-family`: app.1ststep.ai Engineering Orchestrator, app loop and auditor, app implementation agents, resume and partners implementation. The app orchestrator owns implementation of its publisher and decides which content-free metadata may cross into the public-site admin. This site must not read app-owned stores directly or infer their runtime state.

Each producer sends `POST /api/admin-command-center-ingest` with `Content-Type: application/json` and its own `x-1ststep-command-center-key` credential. Set `FIRSTSTEP_COMMAND_CENTER_PUBLIC_INGEST_SECRET` and `FIRSTSTEP_COMMAND_CENTER_APP_INGEST_SECRET` separately (at least 32 characters) in the site environment and distribute each only to its owner. The existing `KV_REST_API_URL` and `KV_REST_API_TOKEN` store one latest snapshot per source, encrypted with the existing `FIRSTSTEP_DATA_ENCRYPTION_KEY` under a source-specific purpose. Keys are server-side only. The browser cannot publish. Source snapshots replace only their own source's previous record. Do not put secrets, customer data, candidate data, repository contents, or private file paths in telemetry.

Minimum payload:

```json
{
  "schemaVersion": 1,
  "contentFree": true,
  "source": "public-ecosystem",
  "observedAt": "2026-09-13T12:00:00.000Z",
  "registryComplete": false,
  "agents": [],
  "projects": [],
  "events": [],
  "audits": [],
  "handoffs": [],
  "decisions": [],
  "releases": [],
  "builds": []
}
```

All records have bounded identifiers and timestamps. Agents report name, explicit status (`registered`, `online`, `working`, `auditing`, `waiting`, `blocked`, `idle`, `stale`, `offline`, `rotating`, or `unknown`), project, task, and owner. Optional metadata includes stable role/scope, cycle, repository and worktree **identifiers** (never private paths), branch/HEAD, finding IDs, heartbeat/activity times, dependency/blocker, and truth state. Missing evidence remains `UNKNOWN`; an old record previously reported active becomes `stale`, while other old records become `unknown`. The publisher must distinguish a recent heartbeat from an open chat and an actual work event from a task label. Counts still require both complete, fresh authority registries. Audit records report explicit status, severity, finding count, owner, remediation owner, re-audit status, and an evidence reference. Handoffs report `from`, `to`, explicit status, optional role/Agent binding and correlation references, and sent/delivery/acknowledgement timestamps; advanced states require delivery and acknowledgement evidence. Releases report status and blocker labels. Build records report status, branch, and commit. See `lib/admin/commandCenter.js` for the exact allowlist and field limits.

Events may carry a minimized envelope: timestamp, kind, summary, project and scoped organization/portfolio/project IDs, Agent/role/runtime/session IDs, entity/correlation/causation/finding IDs, cycle, severity, bounded evidence references, and `truthState` (`OBSERVED`, `AGENT_REPORTED`, `AUDITOR_VERIFIED`, `SYSTEM_DERIVED`, `UNKNOWN`). Omitted truth is `UNKNOWN`. This read model does not store arbitrary event metadata or prove full event history. A model's "build passed" statement stays `AGENT_REPORTED` until an actual build receipt is collected; `AUDITOR_VERIFIED` requires independent evidence. The Activity view filters reported events without changing source data. A future OS backend must own the durable event log and role-routed handoff queue; these latest-source snapshots cannot supply those guarantees. Optional `findings` records display the finding lifecycle in the Audits view; the ingress rejects a reported `pass` without `AUDITOR_VERIFIED`, auditor ID and evidence reference, but the source owner still must independently verify those claims. Release statuses include local, locally verified, independently audited, integrated, preview, hosted verified, release ready, production verified and blocked; the UI never promotes one status into another.

An agent's stable `id` identifies its durable role; a runtime session is a separate, optional `session` projection. Authority publishers may report `session.health` (`healthy`, `degraded`, `stale`, `unreachable`, `watch`, `rotate_soon`, `rotate_now`, `rotation_prepared`, `rotating`, `retired`, `rotation_failed`, `runtime_support_required`, `unknown`), `runtime` (provider/runtime label), opaque `sessionId`, `lastCheckpoint` (`id`, `createdAt`), `rotation` (`id`, `state`, `updatedAt`), and up to 12 `history` entries (`sessionId`, `runtime`, `startedAt`, optional `endedAt`, `state`). Missing projection fields render `UNKNOWN`; stale agent reports force session health to unknown. The exact unsupported rotation state is `ROTATION_REQUIRES_RUNTIME_SUPPORT`. Never publish a transcript, bootstrap text, checkpoint contents, credentials, repository path, or cross-project data through this feed. The Command Center only displays this projection; it cannot start, switch, acknowledge, or retire sessions. The future OS backend owner must supply authoritative lifecycle events under the separate OS lifecycle contract in its own authority domain; this UI cannot infer them from a CLI process or open worktree.

`registryComplete: true` is an assertion that the publisher knows the full registered-agent inventory for **its** authority domain. Leave it false if only a subset or an auditor-only snapshot is available. The UI calculates ecosystem-wide registered/working/auditing/waiting/blocked/idle/offline/stale counts only when both feeds are fresh and both registries are complete; otherwise totals are `UNKNOWN`. A snapshot older than five minutes is not live; an individual record older than five minutes is never counted as working or auditing. The view polls only while visible, every 30 seconds. Polling the UI does not start or control an AI agent.

This contract is a handoff, not evidence that either publisher is already installed. The first public/ecosystem publisher should extract metadata from canonical agent state and the independent auditor's immutable report/inbox, preserving the distinction between **delivered** and **acknowledged**. The app publisher must be implemented and reviewed by the app Engineering Orchestrator. Both should publish a source heartbeat only when an actual collector runs; do not fabricate agent state or reuse a stale payload with a new `observedAt`.

The bounded `npm run command-center:auditor -- --state-dir <auditor-state-dir>` collector is available for the current independent auditor. It reads report/inbox metadata and prints a content-free dry-run summary. With `--publish`, `FIRSTSTEP_COMMAND_CENTER_INGEST_URL=https://1ststep.ai/api/admin-command-center-ingest`, and the public ingest secret configured in that process, it publishes a public-source snapshot containing verified audits and locally delivered handoffs. It intentionally reports **no active agents** and `registryComplete: false`; it reports handoff acknowledgement only from a persisted runtime receipt. The collector does not poll or run autonomously. A later unified public publisher must incorporate this source rather than overwrite it with a separate competing public snapshot.

The same collector now projects `auditCapacity` from the durable Engineering OS `jobs/` and `job-events/` directories when they exist under the approved shared state path. The protected Overview and Audits views display deterministic, free-pool, Claude and disabled paid-provider status plus queue, auto-routable and Claude-escalation counts. An absent state directory or no trustworthy recent provider attempt yields `UNKNOWN`, not `AVAILABLE`; a quota failure yields `USAGE_EXHAUSTED`. This is a read-only, content-free projection. It cannot close a finding, certify a free-model PASS as a release audit, start a provider, or publish by itself. The local collector and admin branch still require exact Preview integration and protected publisher verification before being described as live.

The Audit Orchestrator extension also projects Cloudflare Workers AI free-provider health and the latest 20 durable jobs: finding ID, project, current status/verdict, selected provider/model, event time and cost (`$0.00` only when the persisted verdict used a free or deterministic provider; otherwise `UNKNOWN`). Active-job and pending-Claude counts come from job events, never hard-coded numbers. App-family jobs use app Orchestrator/Loop mailbox pointers and remain UNREAD until those actual runtimes reconcile and acknowledge. No candidate diff, test output, token, or private file path enters this feed. This is a local protected-feed candidate, not verified hosted telemetry.

## Release boundary

The isolated Ship Mode watchdog candidate projects `work/health/latest.json` from the approved public Finish Loop state path. The existing public collector reads it only when under five minutes old, checks reported item IDs/states/owners against the WorkItem journal, and sends bounded owner, state, activity/heartbeat times, waiting reason, next eligible ID and incident counts. The protected Studio Overview and Projects views show `IDLE_FAULT` when eligible public work has no observed owner, `STALE` when a local runtime assertion has aged out, and explained waits for actual decision/audit dependencies. An absent or stale public sweep is `UNKNOWN`; app-family and DaySetGo remain `UNKNOWN` without owner-issued publishers. The preview does not imply those programs have no work. Heartbeat/activity are local runtime assertions, not proof from the provider; this is a read model, not an agent scheduler or automatic runtime adapter. The `work:serve` process is not installed as a supervised service, and no hosted publisher or live Studio feed is verified by this candidate.

This branch is local implementation only. Before production rollout, verify private KV configuration, distinct publisher secrets, the first real publisher, authorization failure cases, local/preview UI, freshness behavior, and rollback. A UI build does not prove live telemetry. Production deployment requires the existing public-site release approval and post-deploy verification.
