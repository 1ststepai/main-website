# Free OS Audit methodology — first-party challenge

**2026-09-13 · Evidence/design review, not six completed Audit runs.** Product direction: [ADR-OS-002](decision-log.md). Inventory: [G1.5 six-system audit](OS_G1_5_FIRST_PARTY_ECOSYSTEM_AUDIT.md). The separate `1stStep OS Audit` has schemas, a fixture/reference scorer and an integration contract, but no scanner, baseline store, CLI engine, production service or finalized real-project run. We used direct repository/document inspection and bounded live HTTP observations to challenge the method. We did **not** create sealed baselines, customer reports, finding IDs, readiness scores, or recommendations to buy anything. A fixture score is never a first-party result.

## Method under test

For an existing build, identify the *canonical project* and authorized surfaces first. Ask for the minimum read-only scope, establish the correct repository, worktree, commit, dirty overlay and confirmed environment, then capture a stable immutable baseline before classifying evidence. Use the existing Audit contract's `state` (CONFIRMED, OBSERVED, INFERRED, ASSUMED, UNVERIFIED, BLOCKED) separately from strength (E0–E4) and repository-vs-live plane. Determine applicable domains from verified project type and an agreed Project Profile/Genome; keep unknown applicability open. Positive evidence belongs alongside negative findings. A gap is a finding only if a control, affected surface, baseline, evidence ID, source/observation time, severity justification, and verification method support it. Absence claims need scoped search coverage. An inaccessible external service is BLOCKED, not clean or broken.

Present verified strengths, evidence-backed weaknesses and risks, material unknowns, and no more than three leading priorities **without hiding** the remainder. Recommend the minimum OS modules/core team roles needed for confirmed work. A specialist is optional and may be unnecessary. Readiness is a qualified statement tied to scope, source plane, freshness and coverage; the current numeric formula's `UNVERIFIED=0` cannot be advertised as observed weakness. With no accepted score-publication gate, do not put an overall number on a free report. A partial public first look must not be called a completed audit.

This sample deliberately spans a public site, a live consumer app, two acquisition surfaces, a non-Git product scaffold, and an unborn Git audit foundation. It tests whether the method distinguishes **Project versus Surface**, source from deployment, read-only inspection from consent to ingest, positive evidence from gaps, unknown from absence, and internal fixtures from customer results. It does not validate audit accuracy or false-positive rates: no engine run or independent adjudicated ground truth exists.

## Method failures and required gate evidence

1. **Project identity and baseline:** G1.5 found multiple worktrees, unknown deployed commits, non-Git OS, and unborn Audit HEAD. The Audit baseline contract needs a verified identity mapping, quiet capture, before/after manifest stability, bounded secret exclusion and an explicit WEAK/UNKNOWN identity path. A website URL cannot be silently equated with a repository, organization, Project or authorization scope.
2. **Applicability / Genome:** The Audit project's 11 type profiles derive from the root ProjectProfile, but root `AGENTS.md` calls Genome undefined (F-0025). Reconcile that mapping and test each of the six surfaces, including multi-surface Job Agent and non-deployed tools, against `NOT_APPLICABLE` and unknown-type controls before emitting priorities.
3. **Audit truth and provenance:** Audit v0.1.0 models pinned, immutable evidence and independent verification but implements only a fixture validator. It failed five upstream schema-lock checks (two unpinned, three drifted), so its contract is **not conformant today**. Review and version changes; do not auto-accept hashes or present fixture output as a working scanner.
4. **Coverage and scoring:** `SCORING_MODEL.md` computes `UNVERIFIED`/`BLOCKED` controls as zero while preserving their labels; `AUDIT_STANDARD.md` formerly required an overall score for every audit. A free report must suppress quantitative readiness until a versioned gate establishes minimum identity, applicable control coverage, source plane/freshness and how unassessed controls affect denominators. Define negative fixtures for missing permissions, unavailable production, partial domains, stale evidence, healthy projects, and contradictory evidence. Do not invent thresholds now.
5. **Finding and recommendation integrity:** Validate a real positive-strength case and a healthy project, not only a recovery fixture. Every top priority needs source, impact, applicability, owner/next step and a possible verification test. Recommendation selection must cite a confirmed need and capability/module version; no agent upsell from a missing fact. Keep full findings and unknowns available beyond the top three.
6. **Authority and privacy:** The OS, Audit, website and Job Agent have distinct owners; Audit G1 ratification is internally contradictory, OS backend owner unassigned, partner/resume release ownership unverified. App data requires an app-orchestrator handoff and project-scoped permission. Set retention/deletion, repository-data exposure, provider processing, audit disclosure and commercial independence before any customer connector.

**Method validation exit:** an independently reviewed, read-only self-audit with a sealed baseline and reproducible evidence; a second unlike first-party Project with verified owner/source/deployment mapping and no cross-project leakage; explicit applicable/unknown controls; verified strengths and adjudicated true/false positives; reproducible findings and remediation/verification; a healthy-project case with no forced upsell; and a demonstrated coverage gate before publishing numbers. Product direction is accepted. The methodology is **specified but not validated end-to-end**, G1 backend implementation remains closed, and G2 persistence must wait for root OS/Audit contract reconciliation.
